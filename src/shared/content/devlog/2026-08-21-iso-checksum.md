> *「굽기 전 30초, 소환진 지문 대조 — 안 하면 사흘을 태운다」*

🗓️ 2026.08.21 (금) · 개발일지 1화 — 스택 왕국 표류기: ISO 다운로드와 SHA-256 체크섬 검증 (macOS 기준)

금요일 밤 11시, 빌드가 세 번 연속 깨졌다. 네 번째를 돌려놓고 의자에 기댄 순간 발밑에서 파란 원이 돌았고, 눈을 떠보니 낯선 대륙이었다.

이름은 **스택 왕국**. 수도는 **루트(Root)**, 성문 밖으로 나가면 **힙 평야**가 펼쳐지고, 그 너머엔 떨어지면 못 돌아온다는 **스택 오버플로 절벽**이 있다고 했다.

나를 부른 건 용사 소환 의식이 아니라 왕국 공방장이었다. 퀘스트는 이랬다.

> "창고에 낡은 골렘이 한 대 있소. 안에 든 정령이 죽었지. 새 정령을 불러 넣어주시오."

…그러니까 우분투 설치였다. 이세계까지 와서.

절차는 원래 세계와 똑같이 단순했다.

1. 정령 소환진이 새겨진 **두루마리(ISO)** 받아오기
2. 두루마리를 **석판(USB)** 에 굽기
3. 골렘에 꽂고 **소환(설치)**

그런데 1번과 2번 사이에 **30초짜리 단계 하나**가 빠져 있었다. 건너뛴 대가는 사흘 뒤에 청구된다. 이 글은 그 한 단계만 다룬다.

## 등장인물

- **셸리** — 검은 창 안에 사는 셸 정령. 무뚝뚝하고, 시킨 것만, 시킨 그대로 한다. 오타까지 그대로 해준다. 입버릇은 "묻지 않은 건 안 해."
- **하슈 영감** — 왕도 뒷골목 각인 감정소 주인. 두루마리에 손을 얹고 64자리 룬을 뽑아낸다. 입버릇은 "지문은 거짓말을 못 하지."
- **나(단타마스터)** — 이방인. 원래 세계에선 개미였고 여기선 견습이다. 어느 쪽이든 물리는 건 똑같다.

## 왜 굳이 지문을 대조하나 — ISO 손상과 체크섬 검증

2.7기가짜리 두루마리를 바다 건너 **미러 상단(商團)** 에서 전송받는다. 이 과정에서 두루마리가 상할 경로는 생각보다 많다.

- 전송 도중 마력선이 끊겼다 이어지면서 일부 구획이 누락된다
- 상단 창고의 사본 자체가 처음부터 불완전하다
- 석판에 옮겨 적는 과정에서 획이 틀어진다
- 드물지만, 미심쩍은 경로로 받았을 때 누군가 손을 댄다

진짜 문제는 이거다. **상한 두루마리도 겉보기엔 멀쩡하다.** 무게(파일 크기)도 비슷하고, 굽기 도구는 아무 불평 없이 잘 구워준다. 이상은 한참 뒤에 나타난다.

- 소환은 시작되는데 중간에 알 수 없는 이유로 멈춘다
- `Errors were found while checking the disk for this installation`
- 소환은 끝났는데 정령의 팔 한 짝이 깨져 있다 (특정 패키지 손상)

여기서 원인을 '두루마리 손상'으로 의심하기까지가 오래 걸린다. 보통은 석판을 탓하고, 골렘의 제단 설정(BIOS)을 뒤지고, 다른 석판으로 다시 굽고… 그렇게 몇 시간이 녹는다. 나도 그랬다. 원래 세계에서 물타기하던 습관 그대로, 안 되는 걸 붙잡고 계속 더 넣었다.

하슈 영감은 그 얘기를 다 듣더니 한마디 했다.

> "굽기 전에 나한테 왔으면 30초면 끝났을 일이오."

## 각인 문양이 뭔가 — SHA-256 체크섬

두루마리 내용 전체를 훑어서 만든 **고정 길이 지문**이다. SHA-256 방식은 64자리 16진수를 뱉는다.

핵심 성질은 하나다. 원본에서 **단 1비트만 달라져도 결과값이 통째로 달라진다.** 앞부분만 비슷하게 나오는 게 아니라 아예 무관한 값이 된다.

그래서 발행처가 공개한 값과 내 두루마리에서 뽑은 값을 맞춰보면, 한 획도 다르지 않은 원본인지 확인할 수 있다.

> 하슈 영감 왈, "획 하나 틀리면 다른 문장이 되는 게 아니라, 아예 다른 언어가 되지."

## 1단계 — 내 두루마리의 지문 뜨기 (shasum -a 256)

macOS 대륙에는 `shasum`이 기본으로 깔려 있다. 따로 구할 필요 없다.

```bash
shasum -a 256 ~/Downloads/ubuntu-26.04-live-server-amd64.iso
```

`-a 256`은 SHA-256 방식으로 뜨라는 뜻이다. 두루마리가 크면 20~30초쯤 걸린다. 진행 표시가 없어서 셸리가 멈춘 것처럼 보이는데 원래 그렇다. 재촉하지 말고 기다리자.

결과는 이렇게 나온다.

```
dec49008a71f6098d0bcfc822021f4d042d5f2db279e4d75bdd981304f1ca5d9  /Users/me/Downloads/ubuntu-26.04-live-server-amd64.iso
```

앞의 64자리가 이 두루마리의 지문이다.

> **다른 대륙에서 오셨다면**
>
> - 리눅스: `sha256sum ubuntu-26.04-live-server-amd64.iso`
> - 윈도우 (PowerShell): `Get-FileHash .\ubuntu-26.04-live-server-amd64.iso -Algorithm SHA256`
> - 윈도우 (CMD): `certutil -hashfile ubuntu-26.04-live-server-amd64.iso SHA256`

## 2단계 — 대공가의 정본 문양록 찾기 (SHA256SUMS)

우분투 두루마리를 발행하는 곳은 **캐노니컬 대공가**다. 대공가는 판본 서고에 `SHA256SUMS`라는 **정본 문양록**을 함께 걸어둔다.

```
https://releases.ubuntu.com/26.04/SHA256SUMS
```

열어보면 이런 목록이다.

```
487f87faaf547ea30e0aba4d5b53346292571256b25333a978db1692bcee9dd2 *ubuntu-26.04-desktop-amd64.iso
dec49008a71f6098d0bcfc822021f4d042d5f2db279e4d75bdd981304f1ca5d9 *ubuntu-26.04-live-server-amd64.iso
```

판본 번호(`26.04`)만 바꾸면 다른 판본도 같은 방식으로 찾을 수 있다.

**중요한 건 이 값을 반드시 대공가 서고에서 직접 가져와야 한다는 점이다.** 어느 여행자 수첩에 적힌 숫자를 믿고 맞춰봤다면, 두루마리를 검증한 게 아니라 그 수첩을 믿은 것뿐이다. 그 수첩이 틀렸을 수도 있으니까. **이 일지에 적힌 값도 마찬가지다. 직접 확인하시라.**

## 3단계 — 대조는 눈이 아니라 셸리에게 (shasum -c)

64자리를 눈으로 대조하는 건 나쁜 방법이다. 사람 눈은 앞 네 자리, 뒤 네 자리만 보고 넘어간다. 그러면 검증을 안 한 것과 크게 다르지 않다.

셸리에게 시키자.

```bash
cd ~/Downloads
curl -LO https://releases.ubuntu.com/26.04/SHA256SUMS
grep 'live-server-amd64' SHA256SUMS | shasum -a 256 -c
```

문양록을 받아서, 필요한 줄만 뽑아, 대조를 맡기는 흐름이다. 마지막 `-c`가 "이 목록대로 검사해줘"라는 옵션이다.

**통과하면:**

```
ubuntu-26.04-live-server-amd64.iso: OK
```

`OK` 한 줄이면 끝이다. 안심하고 석판에 구우면 된다.

**실패하면:**

```
ubuntu-26.04-live-server-amd64.iso: FAILED
shasum: WARNING: 1 computed checksum did NOT match
```

이 경우 두루마리를 태우고 다시 받아야 한다. **고칠 방법은 없다.** 어느 비트가 틀어졌는지 알 수 없으니 재수령이 유일한 답이다. 물타기가 통하지 않는 세계다.

같은 상단에서 또 실패하면 다른 상단(미러)을 쓰거나 토렌트로 받아보자. 토렌트는 조각마다 지문을 맞춰가며 받기 때문에 손상될 확률이 훨씬 낮다.

## 심화 — 문양록 자체가 위조라면 (GPG 서명 검증)

여기까지만 해도 "전송이 깨졌는지"는 충분히 잡힌다. 다만 논리에 구멍이 하나 남는다.

**`SHA256SUMS` 문양록 자체가 바꿔치기됐다면?**

가짜 두루마리를 뿌리는 쪽이 문양록까지 같이 갈아끼우면 대조는 멀쩡히 통과한다. 그래서 대공가는 문양록에 **봉인 인장(GPG 서명)** 을 찍어둔다. 이걸 감정하는 게 **봉인관 지피지**의 일이다.

```bash
cd ~/Downloads
curl -LO https://releases.ubuntu.com/26.04/SHA256SUMS.gpg

# 대공가 인장 받아오기 (최초 1회)
gpg --keyid-format long --keyserver hkp://keyserver.ubuntu.com \
    --recv-keys 0x46181433FBB75451 0xD94AA3F0EFE21092

# 봉인 감정
gpg --keyid-format long --verify SHA256SUMS.gpg SHA256SUMS
```

출력에서 볼 곳은 이 두 줄이다.

```
gpg: Good signature from "Ubuntu CD Image Automatic Signing Key (2012) <cdimage@ubuntu.com>"
Primary key fingerprint: 8439 38DF 228D 22F7 B374  2BC0 D94A A3F0 EFE2 1092
```

`Good signature`가 뜨면 문양록이 대공가가 발행한 그대로라는 뜻이다.

바로 아래에 `WARNING: This key is not certified with a trusted signature!` 라는 경고가 같이 나오는데 놀랄 것 없다. "이 인장을 네가 직접 신뢰한다고 등록한 적은 없다"는 안내일 뿐, 봉인 감정 자체는 통과한 상태다.

> 봉인관이 안 보이면 `brew install gnupg`로 부를 수 있다. 다만 대공가 서고에서 HTTPS로 직접 받았다면 이 단계는 선택에 가깝다.

## 정리 — USB에 굽기 전 세 줄

```bash
cd ~/Downloads
curl -LO https://releases.ubuntu.com/26.04/SHA256SUMS
grep 'live-server-amd64' SHA256SUMS | shasum -a 256 -c
```

`OK`면 진행, `FAILED`면 재수령.

### 오늘의 교훈

원래 세계에서 나는 "예측하지 말고 대응하자"고 매번 다짐만 하다 물렸다. 이세계에 와서 배운 건 그 앞에 붙는 문장이었다. **대응하기 전에, 지금 들고 있는 게 진짜인지부터 확인하라.**

30초를 넣어 사흘을 아끼는 거래다. 그리고 이 습관은 우분투에만 쓰이는 게 아니다. 각종 리눅스 배포판 ISO, 도커 이미지, 대용량 데이터셋, 설치 파일 — **발행처가 해시를 공개했다면 그건 확인하라고 걸어둔 것이다.**

두루마리는 `OK`를 받았다. 이제 석판에 구울 차례인데, 그 얘기는 다음 편에.
