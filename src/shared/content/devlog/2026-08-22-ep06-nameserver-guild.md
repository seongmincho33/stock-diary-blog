> *「도메인 등록업체와 네임서버는 같을 수도, 다를 수도 있다 — dig 한 줄이면 안다」*

🗓️ 2026.08.22 (토) · 개발일지 6화 — AWS 왕국 표류기 ④: 네임서버는 "왕국의 표지석 관리 길드"

두루마리(CNAME)를 들고 영지 등기소에 갔다. 등기소 창구의 대답은 이랬다.

> "영지 등기는 저희가 했지요. 그런데 표지석은… 어느 길드에 맡기셨는지부터 확인해 보셔야겠는데요."

길드? 표지석에 길드가 따로 있다고?

## 프롤로그: 영주(의 대리인)가 된 나 — 도메인을 샀는데 그다음은?

달빛 상단은 얼마 전 **'dalbit-mall.example'** 이라는 영지를 사들였고, 나는 그 대리인이다.

> 이 글의 영지 이름 `dalbit-mall.example`은 예시 전용으로 예약된 이름이라 실제로는 존재하지 않는다. 각자의 영지 이름으로 바꿔 읽으시라.

그런데 영지를 사기만 했다고 끝이 아니다. 영지가 작동하려면:

1. **영지 등기소(도메인 등록업체)** 에 "이 영지는 내 거다" 등록 → ✅ 완료 (후이즈에서 함)
2. **영지 곳곳에 표지석을 세워서 손님들이 길을 찾게 해야 함** → ❓ 누가 관리?

여기서 등장하는 게 바로 **네임서버 길드**다.

## 등장인물

- **등기소(도메인 등록업체)** — 후이즈, 가비아 등. "이 영지는 누구 것"만 기록한다.
- **네임서버 길드** — 영지 안의 표지석을 관리하는 자들. 후이즈 길드, 가비아 길드, AWS 왕실 직속 Route 53 길드, Cloudflare 외세 길드… 여럿이다.
- **셸리** — 이번 화의 마법 주문 담당.

## 네임서버(DNS 서버)란? — "표지석 관리 길드"

```
영지: dalbit-mall.example
표지석들:
  📍 www.dalbit-mall.example → 메인 상점
  📍 m.dalbit-mall.example   → 모바일 상점
  📍 pay.dalbit-mall.example → 결제소
  📍 mail.dalbit-mall.example → 우체국
```

이 표지석들을 **누군가는 관리해 줘야** 한다. 손님이 "메인 상점 어디예요?"라고 물으면 정확히 안내해 줘야 하니까.

이 일을 해 주는 사람들이 **네임서버 길드**다.

> "우리 길드는 당신 영지의 모든 표지석을 24시간 관리합니다! 손님이 길을 물으면 즉시 답변해 드리죠!"

## 역할 정리 — 도메인 등록업체 vs 네임서버

#### 도메인 등록업체 (후이즈, 가비아 등)

```
역할: 영지 등기소 관리
하는 일:
  - "이 영지는 누구 소유인가" 기록
  - 영지 만료일 관리
  - 영지 소유권 이전

비유: 부동산 등기소 직원
```

후이즈 = 영지를 사고 등기하는 곳 (등기소)

#### 네임서버 길드

```
역할: 영지 내부 표지석 관리
하는 일:
  - 표지석 세우기/철거
  - 손님 안내 (DNS 질의 응답)
  - 길 안내 정보 전 세계에 전파

비유: 마을 안내소 + 우체국
```

네임서버 = 영지 안의 길찾기 시스템 운영자

## 헷갈리는 포인트: 등록업체와 네임서버는 같을 수도, 다를 수도 있다

여기가 핵심이다.

#### 케이스 A: 같은 길드가 둘 다 함

```
🏛️ 등기소: 후이즈
🗺️ 표지석 관리: 후이즈
```

영지 등기도 후이즈에서 했고, 표지석 관리도 후이즈에 맡긴 경우. → 모든 작업을 후이즈에서 처리.

#### 케이스 B: 등기는 후이즈에서, 표지석은 다른 길드에서

```
🏛️ 등기소: 후이즈
🗺️ 표지석 관리: AWS Route 53 (다른 길드)
```

영지 등기는 후이즈에서 했지만, **"표지석 관리는 더 좋은 길드한테 맡길게"** 하고 다른 곳에 위탁한 경우. → 후이즈에선 표지석 관련 작업을 못 하고, **Route 53에서 작업해야 함**.

#### 케이스 C: 상단 자체 길드

```
🏛️ 등기소: 후이즈
🗺️ 표지석 관리: 상단 사내 길드 (자체 DNS 서버)
```

큰 상단이 자체 운영하는 경우. 인프라팀에 요청해야 함.

## 그래서 내 도메인의 네임서버는 어디인가

이걸 알아내야 한다. 왜냐하면:

```
"표지석 추가 (CNAME)" 작업은
네임서버 길드에서만 가능
↓
후이즈가 등기만 했다면, 후이즈에서 못 함
↓
실제 표지석 관리 길드를 찾아가야 함
```

등기소 창구가 "확인해 보시라"고 한 게 이 말이었다.

## 마법 주문으로 길드 확인하기 — dig NS / nslookup

**"네임서버 조회 마법"** 이 있다. 셸리에게 시키면 된다.

#### 주문 시전 (터미널)

```bash
dig dalbit-mall.example NS +short
```

또는

```bash
nslookup -type=NS dalbit-mall.example
```

#### 결과 해석

마법진에서 빛이 솟아오르며 길드 이름이 나타난다.

##### 결과 1: 후이즈 길드

```
ns.whois.co.kr
ns2.whois.co.kr
```

> "우리 후이즈 길드가 표지석을 관리합니다!"

→ **후이즈에서 [네임서버 고급설정] 클릭하면 작업 가능** ✅

##### 결과 2: AWS 왕실 직속 길드 (Route 53)

```
ns-1234.awsdns-12.com
ns-5678.awsdns-34.net
ns-90.awsdns-56.org
ns-123.awsdns-78.co.uk
```

> "우리 AWS 왕실 직속 Route 53 길드가 관리합니다!"

→ **AWS 콘솔의 Route 53에서 작업해야 함** (후이즈는 못 함)

##### 결과 3: 가비아 길드

```
ns.gabia.co.kr
ns.gabia.net
```

> "우리 가비아 길드입니다!"

→ **가비아 콘솔에서 작업해야 함**

##### 결과 4: Cloudflare 외세 길드

```
xxxx.ns.cloudflare.com
yyyy.ns.cloudflare.com
```

> "우리 글로벌 Cloudflare 길드가 관리합니다!"

→ **Cloudflare 콘솔에서 작업해야 함**

##### 결과 5: 상단 자체 길드

```
ns1.dalbit-mall.example
ns2.dalbit-mall.example
```

또는 상단 인프라 도메인이 보인다.

→ **상단 인프라팀에 요청해야 함**

## 실제 흐름 시뮬레이션 — 후이즈 등기, Route 53 관리

#### 시나리오: 후이즈가 등기소만, AWS Route 53이 표지석 관리

```
👤 나: "후이즈에서 CNAME 추가하고 싶은데…"
🏛️ 후이즈: "저희는 등기소예요. 표지석 관리는 Route 53 길드에 맡기셨네요."
👤 나: "아 그럼 Route 53으로 가야겠네요?"
🏛️ 후이즈: "네! 우린 등기 정보만 관리합니다."
👤 나: *Route 53으로 이동*
🗺️ Route 53: "어서오세요! 표지석 관리 도와드릴게요!"
👤 나: "_abc123 → _xyz.acm-validations.aws CNAME 추가해 주세요"
🗺️ Route 53: "추가 완료! 몇 분 안에 전 세계에 전파됩니다."
✨ 아크만 길드장의 정찰병: *잠시 후 표지석 발견*
✨ 아크만 길드장: "오! 진짜 영주 맞네! 마법진 발급!"
```

## 근데 왜 이렇게 분리되어 있나 — 도메인 등록과 DNS 운영의 분리

좋은 질문이다. 옛날엔 도메인 등록업체가 다 했다. 그런데 시간이 지나면서:

#### 등기소(도메인 등록)의 일

```
- 도메인 소유권 관리 (1년에 한 번)
- 만료/갱신
- 소유자 정보 변경
→ 자주 바뀌지 않음, 단순 작업
```

#### 네임서버(DNS)의 일

```
- 표지석 추가/수정 (수시로 발생)
- 전 세계 손님에게 빠른 응답 (성능 중요)
- 보안 (DDoS 방어 등)
- 99.99% 가동률 보장
→ 전문성과 인프라 필요
```

그래서 **"등기는 등록업체, DNS는 전문 업체"** 로 분리하는 게 트렌드가 됐다.

#### 분리의 장점

```
🏛️ 등기소(후이즈): 저렴한 등록비
🗺️ DNS(Route 53): 빠르고 안정적인 서비스

= 각자 잘하는 거 하면 더 좋음
```

특히 **AWS Route 53**은 AWS 인프라(CloudFront, S3, EC2 등)와 통합이 잘 되고 응답 속도가 빨라서, **AWS를 쓰는 상단들이 많이 옮겨 간다.**

## 비유 종합 정리 — 도메인·등록업체·네임서버·DNS 레코드

```
dalbit-mall.example (영지)
│
├── 🏛️ 등기소: 후이즈
│   └── "이 영지는 달빛 상단 소유다" 기록
│
├── 🗺️ 네임서버 길드: ???
│   └── 표지석 관리 (이게 누군지 알아야 함!)
│
└── 📍 표지석들 (DNS 레코드)
    ├── A: www → 192.168.x.x
    ├── A: m → 192.168.x.x
    ├── MX: mail → 메일서버
    └── 🆕 CNAME: _abc → AWS (← 추가하려는 것)
```

## 지금 당장 할 일 — 네임서버 확인 3단계

#### Step 1: 마법 주문 시전

셸리의 작업실을 열고:

```bash
dig dalbit-mall.example NS +short
```

#### Step 2: 결과 해석

결과를 보고 어느 길드가 관리하는지 알면, 그 길드로 가서 작업하면 된다.

#### Step 3: 후이즈 화면에서도 확인 가능

만약 터미널을 못 쓰는 상황이면, 후이즈 화면에서:

1. 도메인 정보 영역으로 스크롤
2. **"네임서버"** 또는 **"NS"** 항목 찾기
3. 거기 표시된 값 확인

같은 정보를 얻을 수 있다.

## 한 가지 시나리오 더 — 도메인 관리자에게 직접 물어보기

이 모든 게 복잡하면 가장 빠른 방법:

```
👤 나: "혹시 dalbit-mall.example 도메인의 DNS는 어디서 관리되나요?
        후이즈 자체 DNS 쓰는 건가요, 아니면 다른 곳(Route 53 등)에서 관리하나요?
        AWS 인증서 검증을 위한 CNAME 레코드 추가가 필요한데
        어디서 작업해야 할지 모르겠어서요."

도메인 관리자: "아, 그건 ___에서 관리해요. 거기 가서 추가하시면 됩니다!"
```

상단의 도메인 담당자에게 이렇게 한 번 물어보는 게 가장 정확하고 빠르다. 마법보다 사람이 빠를 때가 있다.

## 캐릭터 시트

```
이름: 단타마스터
직업: 이방인 견습 (Lv. 6)
현재 퀘스트: 달빛 상단 CDN 차원문 봉인
현재 단계: 표지석 관리 길드 정체 파악 중

획득한 지식:
- 📜 도메인 = 영지
- 📜 등록업체(후이즈) = 등기소
- 📜 네임서버 = 표지석 관리 길드
- 📜 DNS 레코드 = 표지석
- 📜 둘이 같을 수도, 다를 수도 있음

새로 배운 마법:
- 🪄 dig NS +short (네임서버 조회)
- 🪄 nslookup -type=NS (대체 마법)
```

### 오늘의 교훈

"등기소에서 했으니 등기소에서 되겠지"는 원래 세계의 "증권사 앱에서 샀으니 증권사가 다 알겠지"와 같은 착각이었다. **소유권을 기록하는 곳과 길을 안내하는 곳은 다를 수 있다.** 그리고 그걸 알아내는 데 주문 한 줄이면 된다.
